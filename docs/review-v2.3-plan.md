## 一、总体结论（打回 · 需修订后重新评审）+ 计数

**结论：打回（Reject / 结构性修订后可再评审）。** 创意方向正确（路线图 `docs/08-roadmap-v3.md:17` 的 v2.3 = "长线目标：收集与轮换驱动"），与 v2.2 相比本稿有实质进步：**这次确实先写了模拟脚本**（`scripts/sim-season.mjs`）、给了 §2.4 预登记集成表、给了 §5 测试计划——v2.2 的 Blocker 2/4 类问题没有重犯。但本稿仍**不具备进入④开发的计划完备度**，且证据链在关键处是自证矛盾的：

1. **§2.1/§3.1 的图鉴口径与脚本输出不一致，且文档自身算术不成立**：§2.1 表头写"共 222 条目"，行内却写"物品 107"，`107+92+9+6+3+8 = 225 ≠ 222`；而 `sim-season.mjs` 实际打印 **物品 104**（`data/items.json` 107 键中 3 件是 `category:'relic'`，脚本按"非遗物"口径计 104）。§7 的 DoD 勾选项写着"§3.1 九项指标与 `sim-season.mjs` 输出逐行一致"——**实测已经不一致**（B1）。
2. **赛季可达性建立在错误的并行模型上**：脚本 E 段明确假设"三条任务【并行】推进 → 全金档耗时由最慢一条决定"。但本作是**单一动作流**（`src/game/settle.ts:47-68` 只推进 `actions.current`，队列是串行的），且三条任务争用同一份矿石与同一份时间。按同口径复算，中期（T3）金档三任务在 24h/日 下需 **12.2~15.8 天**（不是 10.0 天），"留 4 天缓冲"不存在（B2）。
3. **更致命的是时间口径**：D 表所有"天"都以 `÷24` 折算，即假设**每小时都在产出**；而本作离线只结算 `min(elapsed, 8h + 精通)`（`src/game/offline.ts:17-29`）。一个每日上线 2 次的放置玩家实际只计 **16h/日**，中期金档变成 **18~24 天** > 14 天窗口；每日 1 次是 8h/日 → **47 天**。文档通篇未提这个折算系数（B2）。
4. **赛季"重置 + 达到即自动发奖"的核心语义全空**：声望是否清零、等级奖励是否每赛季重发、分档是"只算最高档"还是"铜+银+金累计"、幂等标记存哪、重置瞬间正在达标的边界、门槛未开（总等级<60）期间拿到的图鉴声望去哪——全部未定义；而 §3.1 的 120 声望/20 级曲线**只在"只算最高档"这一未写明的假设下成立**（若累计 10+20+40，单赛季上限 210 声望，20 级模型整体塌掉）（B3）。
5. **"离线期间的产出照常计入，无需额外离线规则"是事实错误**：强化在离线被显式跳过（`src/game/offline.ts:31-46` 跳过当前强化并过滤队列；`src/game/settle.ts:229-231` 期望模式直接拒绝强化），重铸是命令（`src/game/commands.ts:358-393`）——6 条模板里 **2 条（强化尝试/重铸词缀）离线零产出**，而赛季金档强化目标 = 2,000 次 = 中期 25h / 终局 12.5h **纯前台在线时间**（B4）。
6. **"扫描式更新、不在低层埋点"对物品不成立**：材料/装备是会被消耗的（`settle.ts:167-186` 的 `consumeInputs` 在同一个 `simulate` 窗口内先产出后消耗；`automation.ts:10-22` 的自动回收清扫会把离线产出直接卖掉），事后扫描看不到瞬态（B5）。§2.1 说"不埋点"、§2.4 又要"在 `applyRewards`/`reforgeInstance` 埋点"——自相矛盾，且措辞中的埋点位置对词缀是错的（应为 `addInstance`，`src/game/state.ts:99-105`）。

**计数：Blocker 5 条 / Major 10 条 / Minor 10 条。**

### 特别关注项逐条结论（对应任务书 7 问）

1. **数值与证据**：§2 与 `data/*.json` **不一致**（物品 107 vs 104，见 B1）；§3.1 九项与脚本输出**有 1 项数值不一致 + 1 项归因错误**（"最慢一条 = 累计金币"；脚本 D 表里金档"累计金币"只要 9.0 天，最慢是 挖掘/熔炼或锻造/完成远征 三条并列 10.0 天）；"[金/时]"三个数**有据**（= `sim-audit.mjs` B 段 T1/T3/T7：2,812 / 18,527 / 74,845，逐字一致）；但"[轮/时]"三个数是**两套配装基线混用**——金/时用 baseline A（同档 +5 工具、无符文精通），轮/时用满配（+285% 速度）。实测同口径轮速：中期 515 轮/时（脚本取 300，偏保守 1.7×）、终局 382 轮/时（脚本取 578，偏激进 1.5×）、熔炼中期 629 轮/时（脚本取 150，差 4.2×）。**假设偏差 2 倍 → 结论不成立**（见 B2/§五）。
2. **赛季机制可行性**：14 天 × 3 条 × 3 档 × 20 级本身可行，与日常/周常**不冲突**（每槽独立 `base` 快照，`src/game/state.ts` 的 `TaskCounter` 六项齐全：`types.ts:224-235`，`content.ts:56-68` 白名单也已含 `totalReforges/totalExpeditions`）。但赛季槽**不能复用 `TaskSlot`/`taskProgress`**（`tasks.ts:41-52` 的 `defOf` 只认 daily/weekly，赛季 defId 会返回 undefined → 进度恒 0），且抽签**不能复用 `rollDailySlot`**（`tasks.ts:62-75` 用 `Math.random()`，与 S2"确定性"直接冲突）。"达到即自动发奖"在**重置**时的语义、时钟回拨/前拨、门槛期声望归宿全部空白（B3）。压力面：金档要求赛季内**每天 3 次上线**（远征每路线同时只允许 1 个 run，`expeditions.ts:107`；离线不自动续派，`offline.ts:49`）——与放置定位冲突（M9）。
3. **图鉴机制**：`checkCodex` 幂等扫描的**代价实测不是问题**（满图鉴 + 400 件装备 + 60 种材料：**≈7 µs/次**，主循环 250ms×4 ≈ 0.03 ms/s），但"扫描式"对**会被消耗的物品**在语义上不成立（B5）；"曾经持有过"必须落盘这条文档写对了（`meta.codex`）；老档回溯只承认"配方/词缀不可回溯"，**漏了"历史上已被消耗的材料/回收掉的装备也不可回溯"**（m8）；222 条 id 实测 **3,969 B**（文档写 ≈3KB），新档相对增幅 **+165%**（M7），位图**非必要**但建议至少用 `Record<string,true>`/运行时 `Set`。
4. **集成点完整性**：§2.4 共列 11 行，实际至少 **28 处**需改动/登记（§六 逐条 file:line）。完全未提及的必须项：`AchievementType` + `content.ts` 成就校验分支 + `achievements.ts:isMet`（M1）、新表 `data/season.json` 的 `ContentTables`/导入/组装/校验/索引链路（M2）、`src/game/state.ts:9-66` 的 `newGame`（M3，**新档不走 `ensureFields`**，见 `store.ts:220`）、赛季槽的独立结构（M4）、`EPOCH` 的存放位置（M5）。
5. **可玩性与目标结构**：**是目标系统而非产出系统**（赛季满级 62,500 金 ≈ 终局 0.9 小时产出，占终局赛季产出 0.26%）✔ 不构成通胀；但它**不是"顺带完成"的目标**：金档要求把唯一动作流占满 10~16 天，会挤掉 v2.1/v2.2 的重铸/强化/图鉴玩法（M9）。早期/中期/终局体验差异大且**对休闲玩家几乎没有奖励**：铜档 30 声望 = 3 级 = 3,000 金 + 3 精华，而"真正的奖励"徽记只在 **5/10/15/20 级**发放（脚本 `levelReward`），拿不到 5 级就是 0 枚（M6/M9）。
6. **测试计划（§5）**：14 条覆盖了主路径与迁移，但按本稿风险**至少缺 14 条**（§七），尤其：**离线窗口内达标/跨赛季**、**自动回收与图鉴登记的次序**、**赛季槽进度函数**、**分档累计口径**、**幂等标记**、**确定性抽取在全 14 天 × 全赛季键上的穷举**、**门槛期声望**。
7. **UI/移动端**：≤900px **可行**（`App.vue:46-51` 纵向堆叠；`MainPanel.vue:195-204`、`NavBar.vue:169`、`ExpeditionPanel.vue:361-364` 均有既有断点先例），分区卡片单列 + 任务纵排没有问题；把赛季并入图鉴页**方向合理但发现性不足**（剩余天数/未领奖无处醒目），建议在图鉴页签加深色徽标或把"赛季"摘要并入任务页（m7）。

### B2 赛季可达性用错模型：单一动作流 + 矿石争用 + 离线 cap 三重低估，14 天窗口结论不成立
- **章节**：§2.3 第 66 行、§3.1 第 105-107 行、§2.2 第 61 行（"离线期间的产出照常计入"）、§6 风险表（第 143 行）。脚本：`sim-season.mjs:131-135,141-143`。
- **证据 1（架构）**：`settle.ts:41-73` 的 `simulate` 只推进 `state.actions.current`，`advanceQueue`（:75-85）在上一轮结束后才启动队列下一项 → **同一时刻只有一个动作**。脚本 E 段"三条任务【并行】推进"及文档 §2.3"由最慢一条决定"在架构上不成立。
- **证据 2（复算，同口径：同档工具 +5、无符文/精通/词缀，与 `sim-audit` B 段一致）**：

  | 档 | 挖矿 | 开采金/时 | 熔炼 | 锻造 |
  |---|---|---|---|---|
  | T3 银（中期） | **515 轮/时**（脚本取 300） | 18,527（脚本同值 ✅） | 629 轮/时（脚本取 150） | 708 轮/时 |
  | T5 秘银 | 466 轮/时 | 46,636 | 566 轮/时 | 793 轮/时 |
  | T7 虚空（终局） | **382 轮/时**（脚本取 578 = 满配口径 ❌） | 74,845（脚本同值 ✅） | 417 轮/时 | 764 轮/时 |

  金档三任务（挖掘 72,000 轮 + 熔炼或锻造 36,000 次 + 累计金币 4.0M）在**单动作流**下的最短用时（T3，用最省的铜熔炼，矿耗 2/次）：
  `金币 4.0M ÷ 18,527 金/时 = 215.9h`（顺带产出 111,000 挖掘轮，覆盖 72,000 目标）；
  `铜矿 72,000 需挖 38.2h（944 轮/时）+ 熔炼 36,000 次需 38.2h（943 轮/时）`；
  **合计 292.3h = 12.2 天**（若按文档"中期"口径熔炼同级银矿，矿石价值被摧毁 1.94M 金，需多挖 104.7h → **378h = 15.8 天**）。
- **证据 3（离线 cap，文档完全未计）**：`offline.ts:24-29` `counted = min(elapsed, 8h+精通)`，超出部分不结算不结转；`data/config.json` `offlineCapHours=8`，`data/perks.json` offline 上限 +8（深造 ×2 → 最多 24h）。D 表全部 `÷24` 等于假设**每小时都有产出**。

  只有"浏览器常开/离线不超过 8h"的玩家才接近 24h/日——这是**必须写进文档的假设**，而不是默认值。
- **证据 4（归因错误）**：脚本 D 表金档（中期）：挖掘 10.0 / 熔炼或锻造 10.0 / 累计金币 **9.0** / 强化 1.0 / 完成远征 10.0 / 重铸 8.3 天。文档 §3.1 第 105 行的"（最慢一条 = 累计金币 4.0M）"**与自己的模拟输出相反**：最慢是三条并列 10.0 天，累计金币是 9.0 天。同段第 107 行"铜档中期最快 1.0 天"引用的是脚本 `fastestMid`——而该变量取的是 **gold 档**（强化 2,000÷80÷24 = 1.04 天）；真正的"铜档中期最快"是强化 600÷80÷24 = **0.31 天**。脚本标签错 → 文档逐字继承（脚本 `sim-season.mjs:131,140,143`）。
- **修改建议**：①`sim-season.mjs` 增加 **F 段混合排程模拟**：单一动作流 + 矿石守恒（产出/消耗/外卖台账）+ 离线折算系数（24h / 16h / 8h 三档），输出"赛季键 × 三条任务组合"的 20 种抽取下的完成天数分布；② 按 F 段结果**下调金档目标**（若目标是把中期金档压在 14 天内的 16h/日 口径，金档金币建议 ≤2.2M、挖掘 ≤40,000、熔炼或锻造 ≤20,000、完成远征 ≤40——请以 F 段实测回填，勿照抄本行）；③ §2.2/§2.3 写明"每日计入口径假设"；④ 修正 §3.1 的"最慢一条"归因与"铜档最快"标签；⑤ §7 增加"文档数字 = 脚本输出"的**机器校验**（脚本落 JSON，测试逐字段断言）。

### B3 赛季重置与"达到即自动发奖"的语义空白（含分档口径、幂等标记、跨赛季、门槛期、重置瞬间、时钟边界）
- **章节**：§2.2 第 49、59、61 行、§2.4 第 77、83 行、§5 S4/S5（第 125-126 行）、§6 第 142 行、§3.1 第 104、110 行。
- **空白清单（逐条都必须有唯一答案才可实现）**：
  1. **声望是否清零**：§2.2 只说"14 天轮换"，唯一提到清零的是测试计划 S5"重置任务与声望"。若清零 → 等级奖励**每赛季重发**（则 §2.3 的 66,675 金等价是"每 14 天一次"的循环注入，文档应按赛季口径表述）；若不清零 → 20 级 × 6 声望在第二赛季即失效（120 已满），等级奖励永远只能拿一次，整个 14 天循环失去意义。文档两头都没写。
  2. **分档是"最高档"还是"累计"**：脚本 `perTask = TASK_TIERS[last].renown = 40`、`seasonMax = 3×40 = 120`（`sim-season.mjs:66-67`）隐含"**只计最高档**"。若实现为"铜 10 + 银 20 + 金 40 累计"，单赛季上限 = 210，20 级（120）= 8 天可达，§3.1 的 120 与"每级 6 声望"全错。必须写死：**只计最高达成档**（或改曲线并重跑模拟）。
  3. **幂等标记缺字段**：§2.4 的 `SeasonState { index, renown, tasks }` 里**没有** `rewardedLevel`（或 `claimedLevels`）。"达到即自动发奖（幂等，重复调用不重复发）"（S4）在没有持久标记时只能靠"事件只发一次"——但 checkSeason 会在主循环 250ms 一次反复调用（`store.ts:238-250`），且离线/命令后各调一次，**必须**有单调标记，否则要么重发要么漏发。
  4. **重置瞬间正在达标的边界**：前一秒完成任务但 checkSeason 未跑 → 轮换后基线重置，该次达标丢失还是补发？必须写明"先 checkSeason 再 refreshSeason"或反之（建议：**先结算旧赛季的达标与发奖，再轮换**），并写测试。
  5. **门槛期（总等级 < 60）**：§2.2 第 62 行的解锁门槛与 §2.1"图鉴里程碑给声望"冲突——门槛期内完成图鉴里程碑，40 声望**给谁**？赛季状态不存在（或 index 未初始化），若不落地则**永久丢失**（里程碑一次性，codex 永不清空）。必须定义：声望进"待入账池"在下赛季首日补发，或明确"门槛前不计"，并在 §6 登记取舍。

### 5.4 金档三任务的真实排程（单动作流，24h/日）
设 m = 挖矿小时、c = 熔炼小时；矿石守恒：`挖出 = 卖出 + 熔炼消耗`。
- **T3 中期，最省路径（熔炼铜：2 矿/次，铜脉 944 轮/时）**：`金币 4.0M ÷ 18,527 = 215.9h`；`铜矿 72,000 → 38.2h`（顺带 36k 挖掘轮）；`熔炼 36,000 → 38.2h`；**合计 292.3h = 12.2 天**（挖掘 72,000 轮需 139.8h，已覆盖）。
- **T3 中期，同档路径（熔炼银：3 矿/次）**：多摧毁 `108,000 矿 × 18 = 1.94M 金` 等价矿石 → 需多挖 104.7h → **378.1h = 15.8 天** ❌ 超窗口。
- **T7 终局（baseline A）**：`4.0M ÷ 74,845 = 53.4h` 金币需求由挖掘 188.5h（72,000 轮 ÷ 382）覆盖；铜矿 72,000 → 76.3h（944 轮/时用 T7 镐会更快，取铜脉 6000ms ÷ 2.5458 = 2,357ms = 1,526 轮/时 → 23.6h）；熔炼 36,000 → 23.6h；**合计 235.7h = 9.8 天**。
- **T7 终局（满配基线 B，速度 +285%）**：挖掘 72,000 ÷ 578 = 124.6h；铜脉满配 `6,000 ÷ 3.835 = 1,565ms → 2,300 轮/时` → 铜矿 72,000 ÷ (2,300×2) = 15.7h；熔炼 36,000 ÷ 2,300 = 15.7h；**合计 156.0h = 6.5 天**（文档 5.4 天的 +20%）。
- **离线折算（文档完全未计）**：每日上线 2 次 → 实计 16h/日（每次 12h 离线只结算 8h，`offline.ts:24-29`）→ 中期 **18.3~23.6 天**；每日 1 次 → 8h/日 → **36.6~47.3 天**。
- **结论**：文档"中期 10.0 天、留 4 天缓冲"= 并行模型 + 24h/日 + 保守轮速三重乐观叠加；正确口径下中期**没有缓冲**（12.2 天起），16h/日 口径直接**超窗口**。**假设偏差 2 倍 → 结论不成立**（且偏差 2 倍已在文档自身的取值范围内：熔炼速率差了 4.2×）。

- 图鉴一次性徽记 16（3+3+10）叠加后，首赛季中期玩家实际 +32 枚 ≈ **+67%**

### 5.6 奖励价值与通胀
`金 = Σ(500+250×lv) = 62,500（lv1~20）`；`精华 = Σ(1+⌊lv/4⌋) = 25`（×15 = 375）；`徽记 16`（×200 = 3,200）→ 脚本口径 **66,675 金等价/赛季**。
