## 二、逐条验证（B1~B5 + 3 条 Major 抽查）

### B1（伪证据）— 已清零

1. **搜索/邻域代码确实存在**：`scripts/sim-abyss.mjs:218-229` 是真实的循环（`b` 从 `base*0.97` 以步长 0.005 枚举到 `base*1.031`，对三档调用 `reachWith` 判目标带），不是文字描述；输出 `baseSearchHits: 39`（`docs/sim-abyss-output.json:104`），与设计 §2.2 第 42 行"搜了 ±3% 邻域、39 个取值都满足"一致。
2. **"初版单项硬门槛 2/5/5 层"是实算**：`sim-abyss.mjs:246-263`（C 段）有独立实现 `reachSingleStat`，我按同一口径（baseSingle 0.25、growth 1.11、DOM 六项轮转）重写复算，得 **early 2 / mid 5 / end 5**，与 JSON `singleStatReach` 逐值一致；脚本还打印了每档的阻塞点，可验证（前期卡 `quantity` 第 3 层、中期/终局卡 `enhanceRate` 第 6 层）。
3. **定档叙述与算法一致**：设计 §2.2 第 42 行如实写"先定终局 ≈ 35 层，再**反解** `base = 终局战力 / growth^34`"，脚本 `:213-217` 正是 `SCORES.end / 1.0275^34 → 3.1851 → toFixed(3) = 3.185`；"搜索"是对反解值的邻域验证，而非伪称搜索出 base。
4. **残留 Minor**（不改变清零判定）：① 第 43 行"growth 由 2.04^(1/26) 反推 ≈ 1.0275"算术不符——`2.0411^(1/26) = 1.0278`（脚本注释写 2.03，得 1.0276），且指数 26 对应"前期 9 层"，而实测前期是 8 层；② 搜索窗口实际是 **[−3%, +3.1%]**（`:221` 上界 `base*1.031`）；③ 39/39 全过说明该验证无筛选力，文档写"39 个取值都满足"属实，但未提示"终局 35 层是反解的产物、余量仅 0.004%"这一脆弱性。

### B2（画像 caps）— 未清零（本次复审的核心发现）

**独立复算（方法完全按任务给定口径：工具速度按槽位归属、词缀取该槽池 top-N 完美值、工具 ×1.29 / 其他 ×1.5、套装 ≥5/≥8、符文 T3+T2、精通满级、深渊永久 +8% 仅终局）：**

| 项 | early（我 / JSON） | mid（我 / JSON） | end（我 / JSON） |
|---|---|---|---|
| speed | 1.635 / 1.635 | 2.345 / 2.345 | 2.908 / 2.908 |
| efficiency | 0.755 / 0.755 | 1.090 / 1.090 | 1.395 / 1.395 |
| quantity | 0.165 / 0.165 | 0.658 / 0.658 | 0.932 / 0.932 |
| rareFind | **1.450 / 0.500** | **2.020 / 1.070** | **2.400 / 1.450** |
| wisdom | 0.845 / 0.845 | 1.230 / 1.230 | 1.630 / 1.630 |
| enhanceRate | 0.110 / 0.110 | 0.125 / 0.125 | 0.125 / 0.125 |
| **战力** | **4.590 / 3.925（+16.9%）** | **6.916 / 6.251（+10.6%）** | **8.676 / 8.011（+8.3%）** |

五项的复算**逐位一致**，唯一差异精确等于 `0.95 × 0.7 = 0.665` 分——就是 rareFind 符文 T3+T2（0.6+0.35=0.95）被漏掉。**根因（实测）**：

- `sim-abyss.mjs:81` 的 `runeVal` 用 `r.id === \`rune_${effect}_${tier}\`` 原样拼接，`:133` 调用 `runeVal('rareFind', 3/2)` 生成 `rune_rareFind_3/2`；而 `data/runes.json` 的 id 是 **`rune_rarefind_1/2/3`**（全小写）。`node -e` 实测：`rune_rareFind_3 → undefined`、`rune_rarefind_3 → 0.6`。
- 同仓库 `scripts/sim-audit.mjs:42` 的同类 helper 写了 `.toLowerCase()`（`rune_${effect.toLowerCase()}_${tier}`），所以 audit 的稀有口径含符文、新 sim 不含——两份脚本互相矛盾，属复制时漏改。

**后果（不是小数点问题）**：修正后三档战力为 4.59 / 6.92 / 8.68，在文档自己的曲线（base 3.185、growth 1.0275）下可达 **14 / 29 / 37 层**，其中**前期 14 超出 6~12、中期 29 超出 20~28**；即文档"全部命中目标带"的结论**不成立于其自述方法**。±30% 段同理：按 JSON 分复算与文档一致（0~18 / 12~35 / 21~44），按修正分则变为 1~24 / 16~39 / 24~47。

**第二层问题（原 B2 批评的"不可行叠加"仍在）**：`buffs.ts:10` `BUFF_SLOT_COUNT = 2`、单符文 10 分钟，而同一次 `computeStats` 把速度 T3+T2、效率 T3+T2、稀有 T3+T2、祝福 T3 共 **7 个符文增益**常驻计入。按内核约束只取加权最优的 2 个符文（稀有 T3 0.42 + 速度 T3 0.40 = 0.82 分权贡献，脚本口径是 2.075 分），修正后的三档为 **3.34 / 5.66 / 7.42 → 2 / 22 / 32 层**：前期只能过 2 层（6~12 带外），整条"前期 8 层"的结论完全依赖一个不可能同时存在的符文 bundle。

**第三层计时（Minor，但请一并修）**：① 词缀按**原值**取 top-N，而非按加权贡献取——对武器/护甲/饰品槽，加权最优会多出约 0.29~0.38 分（可达层 +2~3），"理论满配"名不副实；② "精通满级"只取基础 `max`，未含 v1.9 深造的 2× 上限（`prestige.ts:20-27`），后者再加 0.89 分。两个方向的偏差都说明 caps 既不是可行 build，也不是真正的理论上限。

### B5（经济出口）— 核心已清零，"永续"措辞未清零

复算（与脚本 E 段、JSON 完全一致）：

- 首轮 4 券：100+130+169+220 = **619**；3 遗物：600；5 级永久：150+195+254+330+428 = **1,357**；称号 200 → **首轮 = 2,776**（= JSON `firstTier`）。
- 终局首通 `crystalToFloor(35) = 1,610`（覆盖 58.0%）；缺口 1,166 ÷ 扫荡 2/次 = **583 次**；常驻 48/日 → **12.1 天**，每日 2 次 24/日 → **24.3 天**，1 次 12/日 → 48.6 天（文档只报前两者，属实）。
- 递增价：第 12 张券 1,792、第 8 级永久 941（四舍五入口径 = §2.5 规则 5 的 `Math.round(首价×1.3^已购)`）。
- **"永续"不成立**：买断全部商品 = 619+…+1,792（券 12 张）+600+941（永久 8 级）+200 = **11,812**（= JSON `shopTotal`），买满后结晶**没有出口**。脚本 `:324` 甚至在同一句里既写"上不封顶的 sink"又写"买满 ≈ 11,812 结晶"，自相矛盾。实机节奏下这个封顶并不小（48 次/日×2 结晶 = 96/日 → 约 123 天；2 次上线 48/日 → 约 246 天），所以原 B5"1.55 天毕业"的系统性问题**已解除**，但"永续/永不无处可花"必须改成"封顶总 11,812 的长线 sink"（或真的放宽上限）。
- **重铸石经济对照**：`sim-affixes.mjs` E 段实测 11.48 石/时（基础口径）~16.72 石/时（满配），单件 T7 完美化 ≈ 20.5 石、十槽 ≈ 205 石。券最多 12 张，且用券**不减免**重铸的金/精华/重铸石成本，只保证一条 id 出现；按"逐条锁定"的 10.5 次/件期望折算，每张券节省的期望次数 ≤ 该槽位份额（~2.6 次 × ~2 石），全生命周期上限约几十颗石（< 1 小时满配采集），且结晶**不可兑换**金币/材料/石头——不会破坏 v2.1 石经济。但设计未量化这条界（Minor，建议在 §2.4 或 §6 补一句）。

## 三、新发现的问题

> B2 未清零的两条根因（rareFind 符文 id 大小写 bug + 7 符文不可行叠加）已在 §二 B2 展开，不在此重复；以下为其余新发现（或旧 Major 残留）。

**Major**

- **M-A §2.2 门槛表与脚本曲线不一致**：表值 3.84 / 4.69 / 5.36 / 6.04 / 6.91 / **7.89** / **9.02**（层 8/15/20/25/30/35/40）对照 base 3.185、growth 1.0275 实算 3.851 / 4.656 / 5.333 / 6.108 / 6.995 / **8.011** / **9.175**，偏差最高 −1.69%（层 35：表 7.89 vs 实算 8.011）。若按表值反推一条自洽曲线（base ≈ 3.137），前期/中期可达层各上移 1 层（9 / 26，终局仍 35）——即这张表与脚本是**两套真值**，照哪套实现结果差 1 层。设计已宣布"全部数值取自 sim 输出"，此表应直接引用 JSON 的 `reqAt`。
- **M-B `AbyssState` 状态模型缺两个实现落点**：① 券余量——`purchased: Record<string, number>` 只记购买次数，券的消耗无字段，§2.5 规则 7.1"有券且券数 ≥1"和 7.5"成功路径恰好消耗 1 张"无处落账（v2.3 初审 m7 要求的 `ticketsUsed` 未登记）；② `permanentSpeed`——§2.1 公式引用 `abyss.permanentSpeed`，但 §2.6 #2 的字段表里没有它（只能从 `purchased['permanentSpeed']` 派生，文档未写）。
- **M-C "永续 sink"表述不实**：见 §二 B5，上限 12 券/8 级 → 11,812 封顶；脚本 `:324` 自相矛盾。应改文案或放宽上限。
