## 一、总评（7.7 / 10）与一句话结论

**总评 7.7 / 10。**

**一句话结论：v2.3 是"工程纪律最好、玩法融合最弱"的一版——"文档数字 = 脚本输出"首次变成机器门禁（S12）、206/17 全绿、迁移与幂等全部经我独立复核通过、图鉴的"源头登记 + 次序契约"在自动回收路径上真实成立；但本版的核心卖点（赛季）在三条既有玩家画像上出现体验断点：离线采矿不进图鉴（8 条矿场分区对放置玩家永久残缺，1 行可修）、离线完成赛季等级**零反馈**（62,500 金静默到账、连摘要弹窗都不弹）、传承后赛季整体锁死（面板反过来告诉 400 级玩家"未解锁"）；同时赛季抽取只有 **6 种组合（去重 5 种）以 6 季为周期硬循环**，远征模板的日历门槛在数值模型里被当成 0 小时，"每日只上线 1 次也能满级"的结论不被覆盖。B1 是一行修复，B2/B3（Major）合计约 20 行，故建议"**先修后放行**"：修掉 B1 + M1 + M2 后，本版应得 **8.4**。**

### Blocker（必须当版修）

**B1 · 离线采矿不登记矿场，8 条矿场分区对放置玩家永久残缺**

- **现象**：`codex.ores` 里面只有**在线**开采过的矿脉。玩家开着页面挖 → 记录；关掉页面/关浏览器让它在离线窗口里挖 → **不记录**。矿场分区（8/222）因此长期停在 1/8，`codex_100`（"百科全书"）与 100% 里程碑对纯放置玩家不可达。
- **证据**：`src/game/settle.ts:140-150`——`recordOre(state, ref.siteId)` 位于 `if (mode === 'online')` 分支内（`:144`），而 `totalMines`（`:138`）、稀有掉落、XP、教程进度三条路径在 `expectation` 分支同样执行（`:146-149`）→ 说明这是**遗漏**而非设计（设计 §2.1 把矿场登记点写作"`settle.applyRewards`（mine 分支）"，未限定在线）。
- **复现步骤（我的临时用例 R1a/R1b，逐字结果）**：
  1. `const s = newGame('T', 0); s.actions.current = { ref: { kind:'mine', siteId:'copper_seam' }, remaining: null, startedAt: 0, durationMs: 0, procMisses: 0 }; s.meta.lastSeenAt = 0; settleOffline(s, 60_000)`
  2. 断言 → **失败**：`s.stats.totalMines = 10`（确实挖了 10 轮）但 `s.codex.ores = ""`（❌ 应含 `copper_seam`）
  3. 对照组 R1b（`simulate(s, 60_000, { mode:'online' })`）→ `s.codex.ores = "copper_seam"` ✅
  4. 真实路径等价：玩家在 8h 离线窗口挖矿 = `startedAt` 在窗口内、回线后 `settleOffline` 走 `expectation` → 该窗口所有矿脉全部不记录。

### Major（登记 backlog，建议当版顺手修）

**M1 · 离线窗口内完成的赛季等级与图鉴里程碑零反馈（计划评审 M8 未真正处置）**

**M2 · 传承（prestige）后赛季整体锁死：面板显示"未解锁"、轮换与结算暂停、跨季奖励作废**

- **现象**：传承把 4 项技能重置到起点等级（精通满级也仅 `1+2×5=11`/项 → 总等级 **44 < 60**），于是 `seasonUnlocked` 变 false：图鉴页的赛季卡片被替换成"总等级 60 解锁（当前 未达成）"（对 400 级玩家显示这句话极具误导性）、任务页的赛季摘要行消失、`checkSeason/refreshSeason` 全部早退——**赛季不轮换、不结算**；等玩家重新练到 60 后，若赛季已跨过边界，`refreshSeason` 直接跳到当前赛季并**清掉旧季声望**，未领取的等级奖励静默作废。
- **证据（我的 R2e/R2f）**：`doPrestige` 后 `totalLevel = 11/11/11/11 = 44`、`seasonUnlocked = false`、`season.index` 冻结在 0 且任务保留；随后 `refreshSeason(s, epoch + 2×SEASON_MS + 1000)` → `index` 仍为 0（门槛未过不轮换）；`checkSeason` 无事件、金币不变（等级 15 之后的奖励无补发）。代码依据：`season.ts:116-117,139`、`prestige.ts:78-84`、`config.prestigeUnlockLevel`。
- **影响**：**这是 v1.5/v1.9 的核心长线循环与 v2.3 核心系统的直接冲突**（本作终局玩家的标准动作就是传承；截图中的档就是总等级 400）。体验上是"我一传承，赛季就消失了"，语义上是"跨季则未领奖励蒸发"。设计 §2.2 硬规则 6 只考虑了"新玩家未解锁"，未考虑"已解锁玩家掉回门槛下"。
- **修复建议（二选一，约 5 行）**：① 解锁判定改为"**曾达到过** 60 级"（在 `meta` 加一个 `seasonUnlockedOnce: true` 标记，首次达标即写死，传承不清）；② 或把解锁判定改为 `totalLevelOf(state) + 传承精通点×N ≥ 60` 之类的补偿口径。同时补 1 条回归："传承后赛季仍解锁、进度与基线不变、跨季照常结算"。

**M3 · 赛季抽取只有 6 种组合（去重 5 种）并以 6 季为固定周期硬循环**

- **现象**：`pickSeasonTasks(index)` 的步骤与游标都只依赖 `index % 6`，因此**全部可能的世界只有 6 种**，且以 6 季（84 天）为周期原样重复；其中 index 1 与 index 3 是同一个集合（`craft+enhance+reforge`，只是顺序不同）→ 实际不同组合 **5 种**。
- **证据（我的 R2g 实测 12 季）**：`["s_mine+s_craft+s_gold", "s_craft+s_enhance+s_reforge", "s_gold+s_reforge+s_enhance", "s_enhance+s_craft+s_reforge", "s_expedition+s_enhance+s_gold", "s_reforge+s_mine+s_craft"]` 然后 6~11 季**逐字重复**；模板出现次数（12 季）：`mine 4 / craft 8 / gold 6 / enhance 8 / reforge 8 / expedition 2`。设计 §2.2 写的是"从 6 条模板按赛季键确定性抽取"，读者会预期 `C(6,3)=20` 种；实现（`season.ts:37-50`）把空间压到 6。
- **影响**：① 长线新鲜感在第 6 个赛季（84 天）后耗尽，此后每个赛季都是"排过的班"；② 组合分布严重偏斜——`enhance`/`reforge`（纯在线）各出现 8/12 季，**5/6 种组合含至少一条纯在线模板**，与放置定位冲突；③ `expedition` 只出现在 1 种组合里（每 6 季 1 次），导致"远征模板的日历门槛"（M4）长期不暴露、一旦抽到就打乱预期。
- **修复建议**：换成"`index` 哈希 + 确定性洗牌"（例如 `mulberry32(hash(index))` 后 Fisher–Yates 取前 3，或直接把 20 种组合按 `hash(index) % 20` 选一种），既保持全服一致/可复现，又把组合空间恢复到 20；测试从"穷举 60 季不重复出 3 条"升级为"穷举 200 季覆盖 ≥18 种组合且各模板出现频次均衡"。

**M4 · 远征模板的日历门槛未进数值模型，`D/E` 段把它当成 0 小时**

- **现象**：赛季耗时模型把"完成远征"模板的耗时记为 **0.0h**（备注"槽位限制,不占动作流"），"每日只上线 1 次也能满级"的结论全部建立在此基础上。但"完成 45 次远征"的真实约束是**日历时间**：每路线同时只允许 1 个 run、离线不自动续派（`expeditions.ts:107`、`offline.ts:52` 只推进不续派），故吞吐 = 路线数 × 每日上线次数。
- **证据（我的 R2h 复算 + 脚本行号）**：`scripts/sim-season.mjs:120-131` 的 `taskHours` 对 `expedition`/`reforge` 一律 `return 0`；`:136-137` 的 D 表因此打印 `expedition 各档 0.0h`。按中期（`outskirts` 需 1 伙伴 + `oldmine` 需采矿 Lv20 = 2 条路线）复算：
  | 中期路线数 × 上线频率 | 吞吐 | 铜 15 | 银 30 | 金 45 |
  |---|---|---|---|---|
  | 2 × 每日 3 次 | 6/日 | 2.5 天 | 5.0 天 | 7.5 天 |
  | 2 × 每日 2 次 | 4/日 | 3.8 天 | 7.5 天 | **11.3 天** |
  | 2 × 每日 1 次 | 2/日 | 7.5 天 | **15.0 天** | **22.5 天** |
  | 4 × 每日 3 次（终局） | 12/日 | 1.3 天 | 2.5 天 | 3.8 天 |
- **影响**：设计 §2.3/§3.1 的"每日只上线 1 次的中期玩家也可满级 ✅（67h/112h = 59.4%）"**对含远征抽取的季节不被证明**（该季银/金档在 1 次/日下需要 15/22.5 天 > 14 天窗口）。结论方向上仍可通过（把远征放铜档 10 声望、另两条冲金 40+40 = 90 ≥ 80），但文档的"最不利抽取 67h、留 40.6% 余量"在含远征组合下实际余量远小于此——这正是计划评审 B2 要求"单一动作流 + 离线折算"的同一类建模漏洞（只补了一半）。
- **修复建议**：① `sim-season.mjs` 的 `taskHours` 为 `expedition` 增加"日历天"分支（`ceil(target / (routes × loginsPerDay))`），E 段按 max(动作流小时/折算, 远征日历天×每日计入小时) 合并；② 把 §3.1 的"满级耗时"改为"动作流 67h ｜ 含远征抽取时受日历门槛约束（2 路线/1 次上线 = 7.5 天铜档，银档超窗）"；③ 或在内容表把金档 45 → 30（2 路线 × 1 次/日 × 14 天 = 28 仍不够）并将"完成远征"模板的**上限档**写死为铜/银。

**M5 · 图鉴里程碑的梯度与获取成本严重不匹配，"均匀 25%"是错觉**

- **现象**：四个档位按**条目数**均匀（56/111/167/222），但六个分区的获取成本差了几个数量级，导致实际体验是"很快到 25%，然后长时间卡在 47%"。
- **证据（我用内容表复算）**：物品 104/222 = **46.8%**、配方 92/222 = **41.4%**，两者合计 88.3%。
  - 25%（56 条）= 早期可达：7 矿石 + 7 锭 + 煤/精华/宝箱/2 试剂 = 18，加 ~20 配方 + ~15 件低级装备 + 1 伙伴 + 1 词缀 + 1 矿场 ≈ 56 ✅；
  - 50%（111 条）= **"拥有全部 104 件非遗物物品 + 7 条"**（含 21 工具/14 武器/28 护甲/10 饰品/12 符文，需锻造 Lv45+ 与 T7 材料）**或**"全 92 配方 + 全 8 矿场 + 全 6 伙伴 + 全 3 遗物 + 2 物品"（后两项是终局内容）；
  - 75%（167 条）= 全物品 + 55 配方 + 全矿场；100%（222 条）需 3 件遗物（`oldmine/ruins/abyss` 各 4.5%/h ≈ 22h/件，其中 `abyss` 需**总等级 150**，`data/expeditions.json`）+ 全 12 符文 + 全 28 护甲。
  - 而 100% 的奖励 = 20,000 金 + 精华 ×40 + 徽记 ×10 ≈ **22,600 金等价 ≈ 终局 18 分钟产出**（四档合计 42,200 ≈ 0.56h）。
- **影响**：收集型玩家会在"就差最后几件 T7 装备/遗物"处长期停滞，而奖励曲线在 50% 之后基本失去驱动力（金/精华对终局玩家无意义，徽记才是主体，四档合计 16 枚）；里程碑的"每 25% 一档"节奏感名存实亡。
- **修复建议**：① 把门槛改为按"分区完成度加权"（如物品 0.4/配方 0.35/其余 0.25）或把档位改为 40/60/80/95%，让梯度贴合成本；② 把 50%/75% 的奖励改成**徽记为主**（如 5/8 枚）或加"图鉴称号/外观"（设计 §8 已把称号推到 v2.5，可提前）；③ 在 UI 的未收集项上给获取提示（出处/等级），降低 47% 停滞期的挫败（见 m2）。

**M6 · 文档数字与实测不符：codex 存档增量"约 1.6KB"，实测满图鉴 3,359 B（差 2.1×）**

- **现象**：设计 §2.1/§2.4 与评审处置表 M7 写"222 条 id 实测 3,969 B，用**逗号分隔字符串压到约 1.6KB**"。实测：满图鉴时四串字符数 **3,311**（`JSON.stringify(meta.codex)` 含包装 **3,359 B**），仅比数组形式（评审实测 3,969 B）**省约 15%**，不是 60%。
- **证据（我在仓库根实跑）**：`items(107) + recipes(92) + affixes(9) + ores(8) = 216` 个 id → 逗号串 3,311 字符 = **3,359 B**（UTF-8，全 ASCII）。新档 +3.4KB ≈ 相对 v9 新档 2,402 B **+140%**，与计划评审 B1/M7 批评的"+165%"几乎同级。
- **影响**：localStorage 配额（5MB）无实际压力，故**无功能风险**；但这是"文档数字 ≠ 实测"的老毛病（v2.2 的 M1/M7 同类），且 §6 风险表用它作为"存档膨胀可控"的依据。
- **修复建议**：文档改为"≈3.4KB 固定上限（随收集度线性增长）；相对早期档增幅最大（+140%）"；位图结论仍可保留（理由改为"配额冗余充足"）。若真想压体积：id 改短码或按分区序号存 Base64 位图（222 bit = 28 B），收益 ~100×，可作为 v3.0 审计项。

## 七、给 v2.4「深渊回廊」的建议（3~5 条，可执行）

1. **先把"离线反馈回路"补上，再叠加深渊的离线进度**：深渊若支持离线刷层，必须同步落地"`OfflineSummary` 增字段 + `settleOffline` 消费所有 `checkX` 返回值 + boot 统一走 `handleEvents`"三件套（本次 M1 的修法）。否则深渊会出现比 v2.3 更严重的"我离线了一晚，层数涨了但什么都没有"。
2. **给深渊写一份"七条硬规则"级别的状态清单，并显式回答"传承后怎么办"**：层数是否保留、词条修饰是否重掷、层数压制与精通点如何换算、离线是否推进/推进上限、越层快照与回退、门槛与解锁、赛季/深渊是否互斥。v2.3 的传承冲突（M2）正是"没写这条规则"的直接后果——v2.4 的深渊与传承耦合只会更深。
3. **沿用 v2.3 已被验证的证据链（这是本版最值得保留的资产）**：`scripts/sim-abyss.mjs` 落 JSON → 测试逐字段断言 → 文档数字取自脚本；并且**脚本必须读 `data/abyss.json`**（别重复 m5 的硬编码）。数值面至少给出三层画像（中/后/终局）的"每层耗时 + 压制强度 + 单位产出"，并对"深渊货币是否成为第二产金通道"做通胀审计（照 v2.2 遗物 `value:0` 的做法）。
4. **把"确定性抽取"升级为有真实多样性的方案**：v2.3 的 `pickSeasonTasks` 只有 6 种组合（M3），深渊的词条修饰/层数事件如果也走"index % N"就会犯同一个错。建议统一实现一个 `deterministicPick(seed, pool, k)`（哈希 + Fisher–Yates），并让赛季在 v2.4 顺手升级到 20 种组合。
5. **收口本次遗留再开新系统**：当版修掉 B1（1 行）+ M1/M2（约 20 行）并补 3 条回归（离线采矿登记、离线事件入摘要、传承后赛季仍解锁）；把 M3（组合多样性）、M5（里程碑门槛/奖励）、M6（1.6KB → 3.4KB 口径）登记进 v2.4 backlog；同步路线图 v2.3 行与"称号 → v2.5"的范围变更（m10）。
